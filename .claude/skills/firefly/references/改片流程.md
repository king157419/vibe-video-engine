# 萤火 改片流程

> 2026-10-12 第四版三部片（峰终、弱关系、赫布）按用户意见改了一轮，用的就是这套做法，效果不错。
> 当天实际跑的脚本存了一份在本 skill 的 `references\scripts\v4-revise-1012-wf.js`（原件在会话目录里，随时可能被清掉）。下面的骨架就是从它整理出来的。

## 目录
0. 用户报了一个时间点：先定位
1. 收到意见：先分类
2. 每部片的修改说明怎么写

## 0. 用户报了一个时间点：先定位

用户说「3:00 好像卡了一下」这类话时，先别假定就是硬静音，也别马上起 Workflow 重渲染（全尺寸一次约 9 分钟）。例子：峰终的硬静音在 [193.15, 196.15]，也就是 3:13–3:16；3:00（180 秒）附近只有 180.75 秒开始的一句新字幕，前面 168.55 秒还有一声换章的 boom。

1. 读 `public\v4\<slug>\subs.json` 和 `cue.json`，列出该秒 ±10 秒内的字幕、`hits`、`silences`（用 Python 写进文件再看，见 `制作命令.md` §10 第 8 条）。
2. 对用户看的那个文件（`成片\...\<字母>_<片名>.mp4`）跑卡顿扫描，`t` 是用户说的秒数：
   ```powershell
   Set-Location 'D:\desk\claudex\24\video-engine'
   & 'D:\conda\envs\d2l\python.exe' tools\v4_stutter.py '<成片里的 mp4>' --from <t-10> --to <t+10>
   ```
3. 抽 t−1、t−0.5、t、t+0.5、t+1 秒的全尺寸帧，用 Read 一张张看：`ffmpeg -y -ss <秒> -i '<成片里的 mp4>' -frames:v 1 D:\tmp\spot\<slug>_<秒>.png`。
4. 判断：
   - 扫出 POP / FREEZE，或者帧里看得出跳变：写进 spec，按 §1 起改。
   - 什么都没查到：先回报「我这边没测到，可能是手机或抖音播放时卡的」，请用户再确认是几分几秒、在哪儿看的。不重渲染。

## 1. 收到意见：先分类

**片子已经发布了的**（比如《峰终》10-12 已发到抖音）：抖音不能替换已发的视频。回复里先说明，新版只能用于 B 站或重发；已发布的那版照常移进 `旧版_<MMDD>\`。

把用户的每一条意见，归到下面两类之一：

| 类 | 例子（10-12） | 怎么处理 |
|---|---|---|
| **明确**：改什么、改成什么都清楚 | 「你要说『比 14 度多 1 度』，把这个点强调出来」；「如果台词能够改成荒草就更好了」；「越亮越冷」不明显（当时直接把亮度差拉大）；某处「卡了一下」（先按 §0 定位，确认真有）；片尾署名改成 Opus 5.5 | 直接进 Workflow。方向清楚、只差幅度的也算这一类，交付说明里写明改了多少 |
| **模糊，或关于整体观感**：只说了感觉，没说怎么改 | 《弱关系》「没那么震撼、没有醍醐灌顶」；《弱关系》缺一句引用（选哪句要用户定） | 先和用户讨论，定了再改 |
| **模糊：只说了位置，没给新词** | 「2:30 那句字幕换个说法」 | 用 `kimi.py` 出 2–3 个候选。中文任务书里附上原句、前后句、字数上限 20、当时的画面，列给用户挑；挑定后再进 Workflow |

这张表可以写进资料夹，也可以直接写进回复里：

`| # | 片子 | 用户原话 | 明确 / 模糊 | 处理 |`

模糊的那几条，回复用户时单独列出来，并给出 2–3 个具体选项供用户挑。例如 2026-10-12 的《弱关系》引用：费孝通被否以后，给的选项是庄子「君子之交淡若水」、《诗经》「他山之石」，或者再找。

## 2. 每部片的修改说明怎么写（写进脚本的 `FILMS[].spec`）

照 10-12 的写法：

1. **引用用户原话**。比如：「我都没反应过来就继续了」。
2. **写清旧台词和时间**。比如：「把 51.50 秒的『多出的三十秒，水只暖了一度，还是冷。』改成两句……」。新台词用用户的原话，或者用户从 Kimi 候选里挑定的那句；Claude 不自己定稿中文。每句 ≤20 字，并提醒 agent 同时改英文。如果这句和某个 hit 或 note 同步，要写进 spec（例如峰终 147.2–153.6 秒「有人听交响乐，二十分钟，美极了；结尾，一声尖响。」对着 155.05 秒的尖响 note），改了长度要连带挪声音。
3. **写清画面上必须看到什么**：出现什么，持续多久（例如「≥3 秒」），和哪一句字幕同步。
4. **写清声音和时长的连锁改动**。例如静音拉长到约 3 秒，后面所有东西都要往后挪：字幕、cue、配乐、画面锚点。再给出片长上限，例如「≤ 4:50」。
5. **给出代码位置的线索**。例如「峰终的署名在 `src\v4\peak\Overlay.tsx` 第 198 行附近」，或者「cue 里的硬静音是 [188.6,190.1]」。
6. **列出用户夸过、必须保住的地方**。例如峰终开场的错音「惊艳」，赫布鲁迅那段「升华了」。
7. **列出这次不做的事**。例如：「不要动《弱关系》的结构，醍醐灌顶的问题要先和用户讨论。」
8. **每部片都加一条：逐个核对叮声**，每一声 bell/ding 都要对上画面上的一个重点。

## 3. 开工前

- **记下开工时间**，在回复里写一句就行，例如「Workflow 14:05 开跑」。万一中途断了，要靠它找出改过的文件（见 §6）。
- **kit 层面的改动由负责人先做好**。修改 agent 不能碰 `src\v4\kit`。10-12 就是负责人先把 kit `EndMark` 的默认文字改成了「Opus 5.5」。
- 确认 `D:\tmp` 存在，D 盘剩余空间够用：三部片同时渲染，每部需要 TEMP 加 out 几百 MB 到 1 GB 的空间【推断】。
- 旧的 `final.mp4` 由修改 agent 自己改名为 `final_<OLD>.mp4`，脚本里写明了这一步。

## 4. Workflow 脚本骨架

**用法**
- 先加载 workflow-authoring skill，照它的 API 写。这套改片 Workflow 用户 10-12 认可过；起之前在回复里说一句「我起 Workflow 改，HH:MM 开跑」。
- 不起 Workflow 的情况：只有一部片、改动很小，或者这次会话没有 Workflow 工具。这时用两个 Agent 子代理代替：先用下面的 `fixPrompt` 起一个修改的，它交回报告后，再用 `verifyPrompt` 起一个独立核查的（两个 prompt 里的 `${…}` 手动填好）。没通过就再修一轮，规矩和 Workflow 一样。
- 把整段脚本通过 Workflow 的 `script` 参数直接传进去。工具会自动把脚本存成文件，并返回路径。
- 之后要改，就编辑那个文件，再用 `{scriptPath}` 重新调用。
- 脚本是纯 JavaScript：不能写类型标注；`meta` 必须是纯字面量；不能用 `Date.now()`、`Math.random()` 和不带参数的 `new Date()`。
- 日期写成常量，或者通过 `args` 传进去。

```js
export const meta = {
  name: 'vibe-revise',
  description: 'Apply the user notes to each vibe film, re-render, and independently verify each film',
  phases: [
    { title: 'Fix', detail: 'one agent per film: edit, re-time, re-score, render, self-QA' },
    { title: 'Verify', detail: 'independent check per film; one repair round if needed' },
  ],
}

// ===== 每次改片要改的常量 =====
const ROOT = 'D:\\desk\\claudex\\24'
const DOCS = '4_第四版资料'      // 第五版改成 '5_第五版资料'
const TODAY = '2026-10-12'       // 写进 自检记录.md 的日期
const OLD = '1008'               // 用户看过的那一版的日期；旧 final 改名为 final_<OLD>.mp4
const MAXLEN = '4:50'            // 片长上限

const COMMON = `
Project root: ${ROOT}. Video code: ${ROOT}\\video-engine (Remotion 4.0.530; run from that dir). Python: D:\\conda\\envs\\d2l\\python.exe (numpy/scipy) — score.py and QA tools need it.
Read first: video-engine\\src\\v4\\CONTRACT.md, video-engine\\src\\v4\\kit\\KIT.md, and your film's ${DOCS}\\<slug>\\自检记录.md (it records the exact build pipeline: timeline/subtitle generator → public\\v4\\<slug>\\subs.json + cue.json → music via tools\\score.py (hebb uses its own score_hebb.py wrapper) → mix → render). Also 剧本.md and 事实核查.md in that folder.

GENERAL RULES FROM THE USER (apply to every film):
- A hard silence after a climax must read as INTENTIONAL, never like the player stuttered: in the same frame the sound cuts, the picture does something clearly deliberate (cut or fast ≤0.25 s fade to near-black, or the hero element freezes while dust/grain keeps drifting), then the next scene fades in. No single-frame pops, no frozen frames while things were moving.
- Every bell/ding must land on a visible on-screen emphasis. Remove or move dings with no matching visual.
- End mark: only the tiny text "Opus 5.5" in the last 2 s — no "由 Claude 用代码生成".
- Key numbers land by contrast ("只暖了1度"), not as two numbers the viewer must compare. When a line refers back to something earlier, bring it back on screen.
- Subtitles: ≤20 字 per line, on screen ≥ chars/4 + 1.5 s; deliberate abrupt stops use a colon or dash. Update the English line whenever the Chinese changes.
- No pencil/handwriting SFX, no harsh dissonant passages.
- Everything the user praised must stay as good as it is.

HARD RULES:
- Edit only: video-engine\\src\\v4\\<slug>\\**, video-engine\\public\\v4\\<slug>\\**, ${DOCS}\\<slug>\\**, video-engine\\out\\v4\\<slug>\\**. Never edit src\\v4\\kit, other films, src\\Root.tsx, package.json; no npm install. Never touch ${ROOT}\\成片 (the lead copies finals there).
- Determinism rules from CONTRACT (no Math.random/Date.now/CSS animation).
- Never hand-edit subs.json/cue.json: change the generator script and regenerate.
- Renders: PowerShell with $env:TEMP and $env:TMP = 'D:\\tmp\\v4<slug>'; --concurrency=5 (the other films render at the same time); delete remotion-webpack-bundle-* in that temp dir afterwards.
- Before overwriting out\\v4\\<slug>\\final.mp4, rename the existing file to final_${OLD}.mp4 if that name does not exist yet (it is the version the user reviewed).
- Windows: do not put Windows paths inside bash heredocs (backslashes get mangled) — write helper scripts to files; do CJK regex in Python, not grep.
- Finish with: tsc --noEmit; music re-synthesis whenever timing or hits changed (score.py uses one seeded RNG, so lengthening a cue changes later reverb/random notes — listen-relevant, mention it); full-size render; two-pass loudnorm mix (I=-16 LUFS, TP ≤ -1.5 dBTP, LRA 7–10, pass 2 linear); final at out\\v4\\<slug>\\final.mp4 with the mixed audio remuxed from mix.wav (no -shortest).
- QA on the new final (required):
  * D:\\conda\\envs\\d2l\\python.exe tools\\v4_stutter.py out\\v4\\<slug>\\final.mp4 — whole film. User-reported spots must be gone; any other POP/FREEZE must be explained as an intentional cut/flash (fast fades show as runs of small POPs — fine).
  * ebur128 loudness; tools\\v4_qa.py as described in 自检记录.
  * Extract full-size frames at every changed moment and actually look at them (Read the image).
- Append "## ${TODAY} 用户反馈修改" to ${DOCS}\\<slug>\\自检记录.md: each change, old → new text/time, evidence frame paths, QA numbers, the exact commands. Update 剧本.md (and 事实核查.md if the wording of a fact changed).`

// ===== 每部片一条：照 §2 的写法填 =====
const FILMS = [
  {
    slug: '<slug>', name: '《<片名>》',
    spec: `
1. <用户原话>。<旧台词 + 秒数> → <新台词（≤20 字），英文同步>。Picture: <必须看到什么、多久、和哪句同步>.
2. <硬静音 / 卡顿：cue silences [a,b]；画面同一帧怎么动；v4_stutter must report no POP/FREEZE there>.
3. End mark → "Opus 5.5" (<署名代码在哪>).
4. Audit every bell/ding for a matching visual emphasis.
User praise to preserve: <夸过的地方>.
Do NOT: <这次不做的事>.`,
  },
  // { slug: 'ties', name: '《弱关系》', spec: `...` },
]

const REPORT = {
  type: 'object',
  properties: {
    summary: { type: 'string' },
    changes: { type: 'array', items: { type: 'object', properties: {
      item: { type: 'string' }, what: { type: 'string' }, new_time: { type: 'string' } }, required: ['item', 'what', 'new_time'] } },
    final_path: { type: 'string' },
    duration_s: { type: 'number' },
    loudness: { type: 'string', description: 'I / TP / LRA as measured' },
    stutter_scan: { type: 'string', description: 'full v4_stutter output and your explanation of each remaining event' },
    open_issues: { type: 'string' },
  },
  required: ['summary', 'changes', 'final_path', 'duration_s', 'loudness', 'stutter_scan', 'open_issues'],
}
const VERDICT = {
  type: 'object',
  properties: {
    pass: { type: 'boolean' },
    checked: { type: 'string' },
    issues: { type: 'array', items: { type: 'object', properties: {
      severity: { type: 'string', enum: ['blocker', 'should-fix', 'nit'] }, where: { type: 'string' }, detail: { type: 'string' } },
      required: ['severity', 'where', 'detail'] } },
  },
  required: ['pass', 'checked', 'issues'],
}

const fixPrompt = (f, extra) => `${COMMON}

YOUR FILM: ${f.name} (slug ${f.slug}). Apply exactly these user notes:
${f.spec}
${extra || ''}
Work through to a finished, mixed, QA'd final. Return the structured report.`

const verifyPrompt = (f, rep) => `${COMMON}

You are an INDEPENDENT reviewer for ${f.name} (slug ${f.slug}). Do not edit anything except scratch files under D:\\tmp\\verify_${f.slug}. The builder claims to have applied these user notes:
${f.spec}

Builder report:
${JSON.stringify(rep, null, 1)}

Check for yourself, on ${ROOT}\\video-engine\\out\\v4\\${f.slug}\\final.mp4:
- Each note is really done: read public\\v4\\${f.slug}\\subs.json for the new text and times; extract full-size frames at the changed moments (and a few frames around them) and LOOK at them. Judge as the user would: is each change obvious and correct on screen, readable on a phone?
- Run D:\\conda\\envs\\d2l\\python.exe tools\\v4_stutter.py on the whole film. The user-reported spot must be gone; any remaining POP/FREEZE needs a convincing intentional reason, otherwise it's an issue.
- Loudness via ffmpeg ebur128: I −16 ± 0.5, TP ≤ −1.5, LRA 7–10. Duration sane (≤ ${MAXLEN}).
- Last 2 s show only "Opus 5.5" as the end mark.
- For each bell/ding in public\\v4\\${f.slug}\\cue.json, grab frames at the hit time and ±0.3 s: is there a visible emphasis on that beat?
- No regressions: compare contact sheets (every 10 s) of final.mp4 vs final_${OLD}.mp4 in the same folder; outside the changed regions the films should match (allowing a time shift after a lengthened pause).
pass=true only if there are no blocker or should-fix issues.`

// ===== 中途被打断后续跑时才填（见 §6）；平时留空 =====
const RESUME_HEAD = `
RESUMING AN INTERRUPTED ATTEMPT: a previous agent started exactly this task and was cut off mid-way by a usage limit (no new final was rendered). Its partial edits are ALREADY in the files listed below. First inspect the current state (read the changed files; compare subs.json / cue.json text and times against the spec; check what each note still needs), then finish the job from there. Do not start over, do not blindly revert, and treat anything half-done as yours to complete or correct. Leftover scratch from the previous attempt may exist under D:\\tmp\\v4<slug> and out\\v4\\<slug>.`
const RESUME = {
  // '<slug>': `${RESUME_HEAD}
  // Files already changed for <slug>: <列表>. <final.mp4 是否已改名 / 音乐是否已重新合成 / 备份在哪>.`,
}

phase('Fix')
const results = await pipeline(
  FILMS,
  f => agent(fixPrompt(f, RESUME[f.slug]), { label: `fix:${f.slug}`, phase: 'Fix', schema: REPORT }),
  (rep, f) => agent(verifyPrompt(f, rep), { label: `verify:${f.slug}`, phase: 'Verify', schema: VERDICT })
    .then(v => ({ rep, v })),
  async ({ rep, v }, f) => {
    if (!v || v.pass) return { slug: f.slug, rep, verdict: v, rounds: 1 }
    const extra = `\nAN INDEPENDENT REVIEWER FOUND THESE PROBLEMS IN YOUR FIRST PASS — fix all blocker/should-fix items, re-render, re-QA:\n${JSON.stringify(v.issues, null, 1)}\n`
    const rep2 = await agent(fixPrompt(f, extra), { label: `fix2:${f.slug}`, phase: 'Fix', schema: REPORT })
    const v2 = await agent(verifyPrompt(f, rep2), { label: `verify2:${f.slug}`, phase: 'Verify', schema: VERDICT })
    return { slug: f.slug, rep: rep2, verdict: v2, firstVerdict: v, rounds: 2 }
  },
)
return results
```

**为什么这样设计**
- **用 `pipeline` 而不用 `parallel`**：每部片修完马上进入核查，不用等最慢的那部。
- **核查 agent 和修改 agent 分开**：Claude 不给自己的活打分，这和用户的「运动员又当裁判」是同一个道理。核查只写 `D:\tmp\verify_<slug>`，不改片子。
- **只修一轮**：第二轮还没过，就把问题带回给负责人，由负责人决定是自己修，还是去问用户。不要无限循环。
- **结构化输出**：`REPORT` 里的 `changes[].new_time` 可以直接填进交付说明的「在哪儿看」；`stutter_scan` 可以直接摘进交付说明，说明哪些 POP 是有意的。

**跑完之后**：逐部看 `verdict.pass`。`rounds: 2` 并且还没过的，读 `issues`，分清是自己能修的，还是需要用户决定的。

## 5. 负责人收尾

Workflow 返回以后，由负责人（主会话）来做。以下示例是第四版的情况，换版本时改 `$V` 和片名。

**1. 抽查：不完全相信 agent 的报告**
```powershell
$py = 'D:\conda\envs\d2l\python.exe'
Set-Location 'D:\desk\claudex\24\video-engine'
foreach ($s in 'peak','ties','hebb') { & $py tools\v4_stutter.py "out\v4\$s\final.mp4" | Out-File -Encoding utf8 "out\v4\$s\stutter_lead.txt" }
New-Item -ItemType Directory -Force D:\tmp\spot | Out-Null
ffmpeg -y -ss <秒> -i out\v4\<slug>\final.mp4 -frames:v 1 D:\tmp\spot\<slug>_<秒>.png   # 每个改动点抽几帧，再用 Read 打开看
```
- 用户报过的位置要逐一看。
- 每部片看一眼片尾的「Opus 5.5」。

**2. 把旧版移进 `旧版_<OLD>\`，再放入新版、同步发布文案**
```powershell
$V   = 'D:\desk\claudex\24\成片\4_第四版_vibe知识大赏'
$DOC = 'D:\desk\claudex\24\4_第四版资料'
$OUT = 'D:\desk\claudex\24\video-engine\out\v4'
$OLD = '1008'
# $films 只放这次改了的片
$films = @(@{f='A_峰终'; slug='peak'}, @{f='B_弱关系'; slug='ties'}, @{f='C_赫布'; slug='hebb'})
New-Item -ItemType Directory -Force "$V\旧版_$OLD\手机预览" | Out-Null
foreach ($x in $films) {
  Move-Item "$V\$($x.f).mp4" "$V\旧版_$OLD\$($x.f)_$OLD.mp4"
  Move-Item "$V\手机预览\$($x.f)_手机预览.mp4" "$V\旧版_$OLD\手机预览\$($x.f)_${OLD}_手机预览.mp4"
  Copy-Item "$OUT\$($x.slug)\final.mp4" "$V\$($x.f).mp4"
  if ((Get-FileHash "$OUT\$($x.slug)\final.mp4").Hash -ne (Get-FileHash "$V\$($x.f).mp4").Hash) { "COPY MISMATCH $($x.f)" }
  $src = "$DOC\$($x.slug)\发布文案.md"; $dst = "$V\$($x.f)_发布文案.md"
  if ((Test-Path $dst) -and ((Get-FileHash $src).Hash -ne (Get-FileHash $dst).Hash)) {
    "发布文案不一致，没有覆盖，请手动合并：$dst"
  } else { Copy-Item $src $dst }
}
```
- 发布文案两份不一致时脚本不覆盖，只打印提醒。先看是资料夹的底稿改了，还是成片里那份被人单独改过，手动合并后再拷。
- 如果片名卡之前的时长变了，片名卡的帧号也会变：要重出封面，并更新发布文案里的封面时间（`制作命令.md` §9）。

**3. 重新出手机预览**
```powershell
foreach ($x in $films) {
  $in = "$V\$($x.f).mp4"; $out = "$V\手机预览\$($x.f)_手机预览.mp4"; $log = "D:\tmp\pv_$($x.slug)"
  ffmpeg -y -i $in -vf scale=1280:720 -c:v libx264 -preset slow -b:v 640k -pass 1 -passlogfile $log -an -f null NUL
  ffmpeg -y -i $in -vf scale=1280:720 -c:v libx264 -preset slow -b:v 640k -pass 2 -passlogfile $log -c:a aac -b:a 96k -ar 48000 -movflags +faststart $out
  Remove-Item "$log-0.log*"
}
```

## 6. 中途被打断后怎么续跑

10-12 的 Workflow 被用量限制打断过一次，三部片都改了一半，还没出新成片。续跑的做法如下。

**1. 先查现状，不急着重跑。** 找出开工以后每部片改过的文件：
```powershell
$since = Get-Date '2026-10-12 14:05'     # 换成 Workflow 实际开跑的时间（14:05 只是示例）
$slug  = 'peak'
$dirs  = "D:\desk\claudex\24\video-engine\src\v4\$slug", "D:\desk\claudex\24\video-engine\public\v4\$slug", "D:\desk\claudex\24\4_第四版资料\$slug"
Get-ChildItem $dirs -Recurse -File | Where-Object LastWriteTime -gt $since | Select-Object FullName, LastWriteTime
Get-ChildItem "D:\desk\claudex\24\video-engine\out\v4\$slug" -File -Filter 'final*.mp4' | Select-Object Name, LastWriteTime, Length
```
`out\` 里的抽帧目录很多，只看 `final*.mp4` 和有没有新的测试片段就够了。

**2. 给每部没完成的片子写一段 RESUME 说明**，填进脚本的 `RESUME`，写清这几件事：
- 哪些文件已经改了，按 src / public / 资料 分开列。
- `final.mp4` 有没有已经改名为 `final_<OLD>.mp4`；有没有新的成片。
- 音乐有没有重新合成：比较 `music.wav`、`mix.wav` 和 `cue.json` 的修改时间。
- 有没有备份（峰终当时有 `out\v4\peak\bak_1008\`）。没有备份的话，告诉 agent 用户看过的旧版在 `成片\...\<字母>_<片名>.mp4`，可以拿来对比。

10-12 写的例子：
> Files already changed for hebb: src\v4\hebb\{Video.tsx, scenes\s4.ts, scenes\s6.ts}; public\v4\hebb\{cue.json, subs.json, timeline_meta.json, music.wav, mix.wav}; 4_第四版资料\hebb\tools\subs_timeline.py; a test clip out\v4\hebb\fix1012\seg_silence.mp4. out\v4\hebb\final.mp4 was already renamed to final_1008.mp4; there is no new final yet. No source backup exists — the 10-08 film is …\成片\4_第四版_vibe知识大赏\C_赫布.mp4 if you need to compare.

**3. 重跑**
- 编辑上次自动保存的脚本文件，把 `RESUME` 填上，然后用 `{scriptPath}` 重新调用 Workflow。
- **已经完成并通过核查的片子，从 `FILMS` 里拿掉**，只重跑没完成的。
- `resumeFromRunId` 能直接复用已经完成的 agent 结果，但改了 prompt 的那个调用，以及它之后的所有调用，都会重新跑。pipeline 里各部片的调用是交错的，可能把已经完成的片子也拖进重跑，等于重新渲染一遍。所以拿掉已完成的片子更稳妥。
- 修复轮（`fix2`）不带 RESUME，这是对的：那时已经是一次完整的结果了。

**4. 提醒自己**：RESUME 的目的是让 agent 从当前状态继续。不要从头来，也不要因为看不懂别人做了一半的改动就整个回退。

## 7. 坑

- **修改 agent 碰了 `成片\`**：脚本里已经禁止。成片文件夹只由负责人改，这样 `旧版_<OLD>` 的移动才不会乱。
- **三部片同时渲染会更慢**：每部 5.5–8.3 分钟，concurrency 都设成 5，不要再调高。
- **重新混音后忘了重新渲染**：弱关系被查出过 P0「成片过期、mix 比 music 旧」。核查时比较 `final.mp4`、`mix.wav`、`music.wav` 的修改时间先后。
- **拉长一段 cue 会改变后面的声音**：score.py 只有一个带种子的随机数发生器，混响和随机音符都会变。交付说明里要提醒用户：「X:XX 以后的配乐细节可能和上一版不完全一样」。
- **硬静音看起来像卡顿**：解决办法是画面在同一帧做明显动作，不是把静音删掉。用户喜欢峰终那个戛然而止，还嫌它太短（「我都没反应过来就继续了」）；《弱关系》《赫布》的问题只是停得不像故意的。
- **时间点要写新片里的**：拉长停顿以后，后面所有时间都往后挪了。「在哪儿看」一律用新片的时间，可以从 REPORT 的 `new_time` 取，再抽帧确认。
